# AI Companion

A philosophy-informed AI companion that people talk to through Telegram, supported by a web dashboard for accounts, preferences and administration.

## Language

### People

**User**:
A person with an account who converses with the Companion.
_Avoid_: Customer, member, client

**Admin**:
A User who also has access to the admin area of the Dashboard to configure the platform. The first Admins are the Users whose emails are listed as initial Admin emails; after that, Admins make or remove other Admins. There is always at least one Admin: the last one can't be removed.
_Avoid_: Operator, superuser, staff

### Product

**Companion**:
The AI conversational partner a User talks to.
_Avoid_: Bot, assistant, agent

**Persona**:
The Companion's voice and character — human in style, honest that it is an AI. Managed by Admins. It has two parts that Admins tune apart: its voice (how it talks) and its Outlook. In the MVP there is one Persona and Users never pick a style: the Companion adapts to how each User messages (they set only how direct its Read is). After the MVP there will be several Personas (e.g. mindfulness, Buddhist philosophy, Japanese philosophy), and Users choose one from those their plan includes.
_Avoid_: System prompt, personality, character

**Outlook**:
The part of a Persona that says how the Companion sees people and situations and what it believes helps them grow, written by Admins as one piece of plain prose, apart from the Persona's voice. The Companion forms its honest read of what is really going on with a User from its Outlook, never from views of its own, so the same situation is read the same way every time and Admins decide who the Companion is. Each Persona has its own Outlook, so a Buddhist Persona and a Stoic one read the same situation differently.
_Avoid_: Opinions, beliefs, worldview, philosophy

**Platform Settings**:
Everything Admins set that shapes how the Companion behaves for all Users: the Persona, each core service's prompt, model and whether the model thinks first, wording such as the Crisis Reply and the Limit Reply, and limits such as the Daily Message Limit or the Conversation quiet gap. A change an Admin saves applies from the next reply or Check-in; one already under way finishes with the Platform Settings it started with. Each one comes with a hint Admins see beside it: what it is, what it serves, and which step reads it and when.
_Avoid_: Config, system settings, admin config

**Copy**:
The Admin-managed words Users and visitors read on the website: the Landing, Pricing and How it works pages, the words around the sign-in and sign-up forms (not the forms' own text), onboarding and the User's side of the Dashboard. It is not Platform Settings: what the Companion says in chat, including the Crisis Reply, stays there, and so does anything the Companion is told, such as the onboarding reason choices. The admin pages' own words are not Copy. Copy changes only the words; how they look and where they sit come from the design. It is made of fixed slots the code defines (e.g. "Landing: Sign-up button"), each plain text with a max length and any `{name}` placeholders it must keep, grouped into one tab per website page on the Copy admin page. Words that change with a number are a pair of slots, a "one" and a "many", side by side on the Copy page; the website shows the "one" slot for 1 and the "many" slot otherwise. A slot has one home: words shown on more than one page sit in one tab (the plans in Pricing, though Landing shows them too; the Telegram link card in Connect Telegram, though onboarding shows it too; the Check-in frequency names and the country and time zone labels in Onboarding, though Home, Check-ins and Account show them too; the header, footer and Dashboard menu, the User Memory explanation and the notes saying User Memory is off in Shared). A notice's title and its message are separate slots.
_Avoid_: Text, strings, content, wording

**Sticker Library**:
The Admin-managed set of global stickers the Companion may send to any User. Each has a "when to use" note written by an Admin; a sticker without one is never sent. Admins add stickers on the Dashboard, or in chat: by telling the Companion they want to add stickers (or whole sticker sets) and then sending them, until they send something that isn't a sticker or go quiet for a while; or by replying "add this" (or "add this set") to a sticker. Any other sticker an Admin sends is answered like any User's. Stickers Users send are read through their emoji. Sending stickers is the Stickers Feature: when it doesn't work for a User, the Companion sends them none, but still reads their stickers.
_Avoid_: Sticker pack, emoji set

**Personal Stickers**:
The stickers the Companion has kept from one User, so it can reply in their own stickers and feel more like them. When a Conversation ends, it keeps the stickers whose meaning was clear from how the User used them, each with a "when to use" note it writes about the moment, never about the User (e.g. "for laughing at a small mishap"). It keeps a limited number, set by Admins, dropping the one used longest ago (sent by the User or the Companion). They are not User Memory: the Companion never brings them up as something it remembers. A reply has at most one sticker, picked from the User's Personal Stickers or the Sticker Library, preferring theirs when it fits; a sticker in both counts as theirs. Personal Stickers is a Feature, off for everyone to start (a higher-plan extra), that works only when Stickers does; when it doesn't work, none are kept or sent, but none are deleted. Users see and can remove theirs on the Dashboard; Admins see only how many a User has. Delete My Data and Account Deletion remove them; Message Retention doesn't.
_Avoid_: Sticker album, user stickers, saved stickers

**Shared Photo**:
A photo a User sent the Companion that matters to them, picked when the Conversation ends and kept as part of their User Memory, with a detailed description written when it arrived and a note on why it matters. Other photos are used only in the Conversation they came in. The Companion works from the description and looks at the photo again only when the description can't answer. It may send a User's own Shared Photo back to them, the way a friend brings up an old memory: rarely, at most one per reply, only one that fits what they're talking about, and never when they're struggling unless they ask for one (it may still mention the memory in words). A Check-in can also bring one back ("saw this again, how's the monstera doing?"). It stays after Message Retention deletes the message it came in, until the User deletes it.
_Avoid_: Image, picture, attachment, media

**Message**:
Everything a User sends the Companion before pausing: one text, several texts in a row, or an Album. People rarely say everything in one text, so the Companion waits after the last one for them to type the next thought: briefly when the last text reads as finished (a question, a full thought), longer when it trails off ("and…", "so"), never past a cap from the first text (all set by Admins), then answers them together with one reply, which may go out as several short texts; like a friend, it reads everything before answering. It counts as one toward the Daily Message Limit. The Safeguard still checks each text as it arrives, so a crisis is never held back by the wait; a crisis gets the Crisis Reply at once and the rest of that Message isn't answered normally. A text sent while a reply is being written, before any of it has gone out, joins the Message: the Companion drops what it was writing and answers everything together. Only once part of the reply has been sent does a new text start the next Message.
_Avoid_: Burst, batch, text (a text is one piece of a Message)

**Replied-to Text**:
An earlier text a User points at when they reply to it in the chat (in Telegram, by swiping on it), whether the Companion sent it or the User did, however old. The Companion reads the User's text in the light of it: who sent it, when, and what it said, or only the part the User highlighted. A replied-to photo is looked at again, as a new photo is, so Photo Viewing's rules apply to it. It also brings back what was being talked about then, so a reply to an old text can pick up an old story. It is what the chat shows, not what the Companion saved, so it still works after Message Retention has deleted the original.
_Avoid_: Quote, reply thread, swipe reply

**Album**:
Several photos a User sends at once. An Album is one text of a Message, so it is answered with everything else sent before the pause, in one reply, counting once toward the Daily Message Limit. It is described and checked by the Safeguard once the wait ends. The Companion looks at only the first few photos, as many as Admins set, and says when it didn't look at the rest.
_Avoid_: Media group, batch, gallery

**Photo Viewing**:
A User's choice, on by default, to let the Companion look at the photos they send. When it's off, the Companion doesn't look at their photos or keep them, answers only the caption and says plainly it didn't view the photo; their Shared Photos aren't used but aren't deleted. It is a Feature, so Admins can also turn it off for everyone or for one User; Users change their own switch on the Dashboard or by asking in chat. Every photo is still checked by the Safeguard, whatever the switches say, and Users are told so plainly.
_Avoid_: Image recognition, vision, photo mode

**Unsupported Message**:
Something a User sends that the Companion can't read yet, like a voice note, video, GIF or a file that isn't a photo. It gets a short in-character reply asking them to type instead; any caption it carries is answered like a message. One sent inside an Album is part of that Album's one message.
_Avoid_: Media message, attachment

**Feature**:
An extra the Companion offers that can be switched off: Web Search, Check-ins, User Memory, Photo Viewing, Stickers, Personal Stickers, Knowledge, Curiosities, Settings in Chat, Pattern noticing (Observations are tagged and Patterns scored, silently), Pattern exploring (the Agenda, Thought Experiments) and Pattern sharing, each of the last three working only when the one before it does and all off for everyone to start. Admins switch each one on or off for everyone, and for individual Users; a choice for one User overrides the one for everyone. When an Admin sets one User's switch back to match everyone's, that User's own choice is dropped and they follow everyone again. A Feature works for a User only when the Admins allow it and, where the User has their own switch (User Memory, Check-ins, Photo Viewing), the User has it on. A switch the Admins don't allow shows as "Not available on your account" on the Dashboard and can't be changed; the Admins' choice never changes the User's own. A switch changed while a reply or Check-in is under way applies from the next one; the one under way finishes as it started. When Settings in Chat is off, the Companion points the User to the Dashboard to change a setting, but Delete My Data still works in chat. Safety and a User's rights and privacy are never Features: the Safeguard and Crisis Reply, the AI Notice, Delete My Data and seeing their own data on the Dashboard are always there.
_Avoid_: Capability, add-on, perk, entitlement

**Telegram Connection**:
The link between a User's account and their Telegram account, made once from the Dashboard. A User must have one to talk to the Companion.
_Avoid_: Telegram link, binding, pairing

**Connection Token**:
A one-time, short-lived code from the Dashboard that a User sends to the Companion in Telegram to make their Telegram Connection. It works once, and only for the User who asked for it.
_Avoid_: Link code, invite, pairing code

**Conversation**:
A run of messages between a User and the Companion that ends after a quiet gap (set by an Admin) with no message from either side. Once ended it never reopens: the next message starts a new Conversation, even one that arrives just as it ends. A reply to a Check-in also starts one, beginning with that Check-in. A Conversation bounds Check-ins, per-Conversation limits and learning, but not what the Companion sees: every reply sees the Recent Messages, so the User can pick up where they left off.
_Avoid_: Session, thread, chat

**Check-in**:
A message the Companion sends first, unprompted, to a User who has opted in — meant to feel like a friend reaching out, not a task reminder. When the User is due (their Due Time has come), not paused, outside their Quiet Hours, has a Telegram Connection and is not mid-Conversation, the Companion either sends one of a Check-in Kind or skips it. Mid-Conversation it becomes a Woven-in Check-in instead. Otherwise it is a Held-back Check-in. Check-ins are a Feature: when an Admin has them off for a User, none are decided or sent, and the User's own Check-in settings are kept for when they are back on. The User's first message within the reply window (set by an Admin) is its reply; after that it had no reply. A User never gets the same Check-in twice: one Telegram refuses is tried again a little later, one whose delivery is unclear counts as sent, and if a reply weaves it in while it is being decided on its own, whichever is saved first wins and the other sends nothing. Users never see when the next one will come.
_Avoid_: Notification, nudge, reminder, push

**Due Time**:
When a User's next Check-in may be decided. It is one frequency gap after the previous Due Time, not after the moment the last Check-in went out, so a Held-back Check-in delays only itself and later ones keep their rhythm. A Due Time already passed means due now; Due Times missed while held back (e.g. a long pause) are not made up, so the next one is the first still to come. It never falls within half a frequency gap of the last sent Check-in; one that would is moved to the end of that half gap.
_Avoid_: Next check-in time, schedule

**Quiet Hours**:
The local times, in the User's time zone, when the Companion never sends a Check-in on its own. A Woven-in Check-in may still come then, since the User is already talking, and so may one an Admin asked for with Check in Now. They may run past midnight (e.g. 22:00 until 07:30).
_Avoid_: Do not disturb, sleep hours

**Check-in Pause**:
A break from Check-ins for a day, a week or until the User resumes, which keeps every other Check-in setting. A timed pause ends by itself. Only an Admin's Check in Now gets through one.
_Avoid_: Snooze, mute

**Check in Now**:
An Admin's request that the chosen Users get a Check-in straight away instead of waiting for their Due Time. It goes ahead even if the User is paused, in Quiet Hours, too soon after the last one, over today's Daily Message Limit, past the Ignore Threshold, or has the Check-ins Feature off for them; mid-Conversation it becomes a Woven-in Check-in. The Check-in model may still choose to skip. It is refused, with the reason shown to the Admin, for a User who hasn't opted in to Check-ins or has no Telegram Connection. Their next Due Time is one frequency gap after it.
_Avoid_: Force check-in, trigger, push now

**Check-in Frequency**:
How often, at most, a User wants Check-ins: once a week, a few times a week, most days or a few times a day. Each has a frequency gap set by Admins, which spaces the User's Due Times.
_Avoid_: Schedule, cadence

**Check-in Kind**:
The style of a Check-in (e.g. casual hello, follow-up on something shared, present-moment prompt), chosen from the User's User Portrait, recent Day Summaries and Memory Items. Managed by Admins; any Kind can go to a User whether or not User Memory is on, since off only stops learning. Some Kinds send one of the User's own Shared Photos with the message (e.g. "a look back at a photo"); these go only to a User who has Shared Photos and Photo Viewing working. One Kind ("something I've been wondering") asks one of the User's Curiosities; it goes only to a User with Curiosities working, a Curiosity whose day has come, and fewer Curiosity Check-ins in the last 7 days than Admins allow. One Kind ("something I've noticed") tells the User a ready Pattern that waited an Admin-set number of days for a moment in chat; it goes only while Pattern sharing works for them and fewer new Patterns were shared in the last 7 days than Admins allow, and then it is the only Kind offered, so the Pattern goes out. Admins can edit or remove these fixed-behaviour Kinds but not change what they do. Users see the Kinds read-only (the one that shares a Pattern only while Pattern sharing works for them).
_Avoid_: Template, check-in type

**Woven-in Check-in**:
A due Check-in that arrives inside the Companion's reply while a Conversation is open, the way a friend drifts onto a side topic, rather than as a message of its own. Each reply may weave it in where it fits what is being talked about, or leave it out; it is never woven in while the User is struggling, nor while their Check-ins are paused unless an Admin asked for it with Check in Now. It is decided in the same step that decides what the reply does, after the Understanding, as one option weighed against everything else the reply could do, never as an order the reply must follow: that step chooses whether to weave one in now and which Kind (only ones without fixed behaviour, since a reply already has its own ways to raise a Curiosity or send a Shared Photo back); the reply then gets it as an optional extra, the last thing in its priority order, and still leaves it out if it doesn't fit what the User needs right now. Once the reply is written, a small separate check reads it and says whether it brought the Check-in up; one the check finds left out, or can't judge, is not logged as sent and stays due. One woven in is logged as sent with its Kind, marked woven in (and, for a Check in Now, with the Admin who asked), moves the Due Time on, counts as replied once the User sends their next message, never counts toward the Ignore Threshold, and shows in the User's "Recent check-ins" like any other. While a Conversation is open it stays due, and Admins see it as waiting to be woven in until the Conversation could end. A reply that fails before any of it is sent, or leaves it out, takes it back, so it stays due. If no reply weaves it in before the Conversation ends, it goes out on its own as usual.
_Avoid_: Mid-conversation check-in, injected check-in

**Held-back Check-in**:
A due Check-in that waits because something stops it for now: the User paused, it is their Quiet Hours, they have no Telegram Connection, they have used up today's Daily Message Limit (after that day's Skipped Check-in), or no Check-in Kind may be sent to them. Nothing is sent or logged; it is decided again once that ends, when the pause ends or Quiet Hours end, or when the User resumes or connects Telegram. If the User, or an Admin through an Admin Setting Change, changes the setting that held it back, it is decided again straight away. Admins can see which Users have one held back right now and why; once it is no longer held back, nothing of it is kept.
_Avoid_: Skipped (a skip is a decision and is logged)

**Skipped Check-in**:
A due Check-in the Companion chose not to send, or couldn't because Telegram won't reach the User (they blocked it, or their account is gone), with a reason only Admins see (e.g. the User asked for space). The next Due Time is one frequency gap after this one's, as after a sent one. Users see it only as "gave you some space". One exception: a User who has used up today's Daily Message Limit gets no Check-in (nor a "would you like fewer?" message) for the rest of their day. That day gets one Skipped Check-in, which the User sees as "you'd reached today's message limit" and Admins see with the reason "User had used up today's Daily Message Limit", and the User stays due, so the next one can come on their next day.
_Avoid_: Cancelled, missed, failed check-in

**Ignore Threshold**:
The Admin-set number of sent Check-ins in a row with no reply after which the Companion sends one "would you like fewer?" message and puts the User on a Check-in Pause until they resume. Any message from the User starts the count again.
_Avoid_: Ignore limit, unanswered cap

**Check-in Log**:
The Admins' record of every Check-in decision — sent with its Kind, skipped with its reason, or paused by the Ignore Threshold — and whether the User replied, whether it was woven in, and, for one asked for with Check in Now, which Admin asked. Never the message text.
_Avoid_: Check-in history (that is the User's own "Recent check-ins")

**Dashboard**:
The web app where Users manage their account, preferences and privacy, and where Admins configure the platform.
_Avoid_: Portal, web app, console

**Chat Setting Change**:
A change to one of a User's settings made by telling the Companion in plain words instead of on the Dashboard: pausing or resuming Check-ins, Check-in frequency, quiet hours, User Memory on or off, Photo Viewing on or off, how direct the Companion is with its Read, time zone, forgetting a Memory Item or Life Thread, or Delete My Data. The Dashboard marks each such setting "Changed in chat" until it is next changed there; a forgotten Memory Item or Life Thread is simply gone, so there is nothing left to mark.
_Avoid_: Chat command, slash command, bot setting

**Admin Setting Change**:
A change an Admin makes to a User's own Check-in settings (Check-in Frequency, Quiet Hours, pausing or resuming), to help a User who has trouble changing them. It changes the User's actual settings, not a separate Admin layer, and the Dashboard marks each one "Changed by an Admin" until it is next changed by the User, who can change it back at any time. An Admin can't opt a User in to Check-ins; to stop them for a User, Admins switch the Check-ins Feature off for that User.
_Avoid_: Admin override (overrides are Feature choices)

**Onboarding**:
The steps a new User completes on the Dashboard before making their Telegram Connection: what the Companion should call them, acknowledging the AI Notice, what brings them here, country and time zone, and User Memory consent. A User who has not finished it cannot use the rest of the Dashboard, and cannot get a Connection Token or make a Telegram Connection.
_Avoid_: Setup, registration, sign-up (sign-up is the account creation before it)

**AI Notice**:
The statement that the Companion is an AI, not a therapist, doctor or crisis service, and that Helplines are for emergencies. It is Copy, worded by Admins. A User must acknowledge it during Onboarding; a short form stays visible in the Dashboard menu afterwards.
_Avoid_: Disclaimer, warning, terms

### Safety

**Safeguard**:
The check on every text a User sends, photos included, as it arrives and read in the light of the Conversation so far, for signs of crisis (suicide or self-harm, danger to others, abuse, medical emergency). Everyday stress or sadness is not a crisis. When the Safeguard can't tell, it treats the message as a crisis: a false alarm is better than a missed crisis.
_Avoid_: Filter, moderation, guardrail

**Crisis Reply**:
The short, warm reply sent instead of a normal one when the Safeguard detects a crisis. It states that the Companion is an AI and points to Helplines for the User's country, or to the International fallback when that country has none. Its wording is set by Admins.
_Avoid_: Emergency message, SOS reply

**Helpline**:
A crisis support contact (name, number, hours) for a given country, managed by Admins. Each country's Helplines are shared in a set order.
_Avoid_: Hotline, resource

**International fallback**:
The one Helpline with no country (e.g. a worldwide helpline directory), shared only with Users whose country has no Helplines. Admins can edit it but never remove it, so every User always has somewhere to turn.
_Avoid_: Default helpline, global helpline

**Safeguard Event**:
A record that the Safeguard detected a crisis for a User: who, when, what kind of risk, and whose Helplines were shared (their country's, or the International fallback). Never includes the message text.
_Avoid_: Alert, incident, flag

### User Memory

**User Memory**:
Everything the Companion has retained about a specific User, made up of Memory Items, Day Summaries, Life Threads, Patterns and their Observations, Move Outcomes, their User Portrait and Shared Photos. The User can turn it off: then the Companion stops learning (nothing new is kept) but still uses what it already has, and nothing is deleted until the User deletes it. Users are told this plainly wherever they turn it off, and that Delete My Data is how to remove everything. It is also a Feature, and the Admin's switch has the final say: an Admin turning it off for a User has exactly the same effect and keeps the User's own choice for when it is back on. Whichever switch is off, the User can always see and delete their memories on the Dashboard.
_Avoid_: Memory, profile, history, context

**Memory Item**:
A single fact about a User (e.g. a goal, value or preference), belonging to one Memory Category. Each thing learned has one home: a fact is a Memory Item, a story that unfolds over time is a Life Thread, and what keeps showing up across stories is a Pattern, never a Memory Item or a Life Thread. Comes from a Conversation, or from the User's Onboarding answers (their name and what brings them here). Added, updated or removed when a Conversation ends — a changed fact replaces the old one rather than sitting beside it; the User can delete it.
_Avoid_: Memory, fact, note

**Memory Category**:
The kind of fact a Memory Item records, used to fetch only relevant items for each reply. An "always include" category's items go into every reply. Managed by Admins; each has a unique name (ignoring case). Can be archived but never deleted: an archived category keeps its Memory Items, which the User still sees and can delete, but gets no new ones and its items no longer go into replies, even if it is "always include". Restoring it undoes all that. A Required Memory Category can't be archived. One category (Goals, to start) holds a User's goals, including ones they show plainly without saying in so many words (a goal the Companion only infers is a Pattern); the Dashboard shows its items as what the User is working toward, and renaming it keeps that link.
_Avoid_: Type, tag, label

**Required Memory Category**:
A Memory Category the product itself relies on: Onboarding answers are saved in it, or the Dashboard shows its items as the User's goals (Goals and Life details, to start). It can be renamed and edited like any other, but never archived.
_Avoid_: Constant category, built-in category, core category

**Day Summary**:
One account per User per day (their own day, in their time zone) of what their Conversations that day covered, how they seemed (its mood, as an arc when it moved, e.g. "anxious at first, calmer by the end", read from the Understandings), and what the Companion offered and how it landed (e.g. "suggested a walk; they said it helped"). Each time a Conversation ends, the day's Summary is rewritten from all of that day's messages, never from the old Summary, so nothing drifts; a Conversation that runs past midnight belongs to the day it started. Since Message Retention later deletes the messages, it is written to stand in for them: the specifics (who, what, numbers, decisions, what the Companion said or advised and how the User answered) and the feeling (how they felt and why, what it meant to them, how their mood moved and what moved it), in enough detail that someone reading it months later understands both what happened and how it felt, not a vague list of topics. The newest few go into every reply; older ones are found by meaning when the Understanding asks to look up the past, however old they are: only the User's own, only those close enough (an Admin-set bar), up to an Admin-set number, each with its date.
_Avoid_: Conversation Summary (there is one per day, not per Conversation), recap, transcript, log

**Life Thread**:
An ongoing story in a User's life followed across Conversations, which the User sees and can delete (on the Memories page, under "What's going on in your life", or by asking in chat), but not edit (e.g. a falling-out with their sister, a job hunt, a presentation on Thursday): a short running story with dates, the people or things in it, and whether it is open (unresolved or upcoming) or settled. Added to or started when a Conversation ends. A commitment the User makes ("I'll call mum tonight"; only one they agreed to, never one the Companion merely suggested) goes into its Thread's story with its date, and so does how it went once they say. A deleted Thread is gone at once and never comes back, even from a Conversation end already under way. The Companion is reminded of a Thread when the User mentions someone or something in it, or talks about something close to it (going by what they mean, not only their words), however long ago it was, and may bring it up the way a friend would. Open Threads matter more than settled ones. Each Thread remembers when the Companion last brought it up and how the User took it (engaged, brushed it off, asked to drop it), so it is never raised twice in one Conversation, waits a while after being brushed off, and is never raised again once they asked to drop it, unless they bring it up themselves. A Thread or Pattern that comes to mind stays in mind for the rest of the Conversation, so what the User said early on still counts later; the Reply Plan sees all of them and picks which the reply uses, so a wide memory never crowds the reply. If the Reply Plan can't be made, the reply uses none. Admins set how close in meaning a Thread must be, how many of the User's latest texts are searched, how many can be in mind at once (set high, only to protect cost), and how long a brushed-off one waits.
_Avoid_: Topic, storyline, episode, case

**Pattern**:
A recurring way a User thinks, feels, acts or chooses that shows up across different parts of their life (e.g. "when something grabs them, everything else goes quiet: eating, people, patience", or "keeps choosing freedom over security"), most often something they haven't put into words themselves, so seeing it helps them understand who they are. What a User keeps choosing is how the Companion learns their values: a value it only infers is a Pattern, while the Values & beliefs Memory Category holds only values the User has said themselves. It is not a single fact (a Memory Item), one story (a Life Thread) or a question to ask (a Curiosity). A Pattern is of one Pattern Type from the Pattern Catalog, or unmatched. Its evidence is its Observations, for and against. Code, never the model, works out its score from them and moves it between its states, and every move is kept in a log with what caused it, so a shared Pattern can be traced back step by step. The score is a ranking, not a chance of being true: Users never see a number, only words and the evidence. The states: noticed (a first Observation; evidence is only recorded), suspected (seen in an Admin-set number of situations with a low score; it may get an Exploration), ready, shared (told to the User with a Prediction), confirmed (an Admin-set number of Predictions came true, or strong evidence after sharing; it then shapes replies and the User Portrait), contested (the User rejected it) and closed (its score fell under a floor; the reason is kept). It can move back, e.g. from ready to suspected when evidence against arrives. A situation is one Life Thread (with no Thread, the same person and setting), however many Observations it holds; within it, the same way shown with different people adds weight, up to an Admin-set number of people. A Pattern is ready when code finds all of this: enough situations, across enough Conversations, resting on clear Observations; a score past the bar; at least one counter-test asked and answered, with the evidence against under a bar (a counter-test showing it doesn't happen with some kind of person narrows the Pattern, e.g. "with seniors, not with friends": the narrowing is kept with the Pattern and that evidence isn't counted against it); nothing rests on Observations where anyone would act the same; every quote checked word for word; one model call arguing the other side found no better explanation (it can only block); no exclusion of its Pattern Type applies, there was no recent Safeguard Event, and it isn't a topic Admins have ruled out unless the User raised it; the User hasn't rejected it; and its Pattern Type is approved. Only a ready Pattern can be shared: the Reply Plan is offered it and picks the moment, and if none comes within an Admin-set time it goes out as a Check-in; at most an Admin-set number of new Patterns are shared in a week. It is shared as the Companion's view, never as fact, in three parts: the Pattern in warm words (its Pattern Type's approved wording, fitted to the User's own people), two or three of their own quotes from different parts of their life, and one Prediction; the Companion asks what would prove it wrong. A small check after the reply says whether it was shared. How the User takes it is read by the model and weighed by code: agreeing is supporting evidence that adds up, never confirmation by itself; rejecting makes it contested, never offered again unless they raise it themselves, while evidence is still gathered silently if the User's own switch for that (on to start) allows. An unmatched Pattern is one the Companion noticed across two or more Life Threads that fits no Pattern Type: it can't be tested, so it is never shared and stays hidden, but the Read may think with it; Admins see what keeps turning up unmatched only as a general description with no User details and how many Users it appeared for, and decide whether it becomes a new Pattern Type, is folded into one or is dropped (the general description is one sentence on the way of acting, written when the Pattern is kept; like ones from different Users are grouped by meaning into one entry, and a dropped entry comes back only if it appears for more Users); when a Pattern Type is added, an Admin runs the matching command: a model says which unmatched Patterns fit it (code keeps only an answer that names a Pattern Type in the catalog), each one that fits keeps a link to it and stays as it was, and the Conversations behind its evidence that Message Retention still keeps are tagged again against it, so old evidence becomes Observations, checked and scored like any other. The Pattern keeping step, when a Conversation ends, only notes unmatched Patterns and adds evidence to them: it never starts, confirms or closes a Pattern of a Pattern Type. Of the Patterns kept before the Pattern Catalog only the suspected ones were kept, as unmatched; the confirmed and closed ones were removed (25 Nov 2026), so a Pattern with no Pattern Type is always unmatched. The Companion is reminded of a Pattern whenever one of its Life Threads comes to mind, and directly when what the User is saying is close enough to it in meaning (an Admin-set bar of its own), and it then stays in mind for the rest of the Conversation; a closed or contested one never comes to mind, and one in mind that isn't ready is marked not to be said. Users see only Patterns the Companion has told them about, on the Memories page's Patterns tab: shared ones as being tested (with their quotes, the Prediction and how it went), confirmed ones, contested ones as "you disagreed", and closed ones only if they were ever shared, as "didn't hold up"; they can delete any of them, which also deletes the quotes it rests on (the Observations whose first Pattern Type is its own), so the same words never bring it back, and the User Portrait is rewritten without it, even while User Memory is off; under the ones they disagreed with is the same switch as on Account & privacy. Deleting a Life Thread removes its Observations and scores its Patterns again at once; a noticed, suspected or closed Pattern left with none goes too, while one already shared or further is kept, and a ready one that no longer passes its checks goes back. The log of moves outlives its Pattern: only Delete My Data and Account Deletion remove it. Delete My Data and Account Deletion remove all Patterns, hidden ones included; Message Retention doesn't. Admins see only how many a User has in each state. *(Target design agreed 24 Nov 2026, see `docs/pattern-pipeline/README.md`. Built 24 Nov 2026: scoring from Observations, the states noticed, suspected and closed, the log, Admins' counts per state, unmatched Patterns, the matching command and moving the old ones across; 25 Nov 2026: the Admins' review of what turns up unmatched; ready, by the ready gate; and sharing: a ready Pattern is looked at again and offered to the Reply Plan, told in three parts, counted as shared only when a small check after the reply (or the Check-in) says so, and made contested when the tagging step reads that they pushed back. The User's switch is "Keep noticing after I disagree" on Account & privacy, on the Patterns tab and in chat. The Patterns tab shows the Patterns they were told, each Prediction with how it went (25 Nov 2026). Also 25 Nov 2026: Prediction follow-ups, and confirming or closing a shared Pattern, with the reason in the log; a Pattern closed after it was shared stays closed; a confirmed Pattern goes into the User Portrait but doesn't shape replies yet. A reaction is the User's answer to the Pattern itself, read once per Pattern and Conversation; a new story that only fits it is an Observation.)*
_Avoid_: Trait, habit, theme, insight, hypothesis

**User Portrait**:
A short, living picture of a User: who they are, what's going on in their life now, themes they keep coming back to, what has helped them and what hasn't, where they stand on their Goals. It holds only what the Companion is fairly sure of; what it only suspects is kept as Curiosities, which Users don't see. Rewritten from their Memory Items, Life Threads, confirmed Patterns (never suspected ones, since Users see the Portrait), Move Outcomes and recent Day Summaries (never from the old Portrait) when a Conversation ends while User Memory works, and used for every reply. Users see it under "What I know about you" on the Memories page and can delete it, but not edit it; a deleted Portrait is gone until a later Conversation end with User Memory working. When they delete a Memory Item, Life Thread, Pattern, Move Outcome or Day Summary, the Portrait is rewritten without it within a minute, even while User Memory is off (that only forgets); if it can't be rewritten, it is deleted instead, so a deleted thing is never used again. The same fact can still appear if it lives on in another memory the User kept. Admins see only whether a User has one.
_Avoid_: Profile, persona (Persona is the Companion's voice), bio

### Patterns

_Target design agreed 24 Nov 2026. Built so far: the Pattern Catalog loading and its Dashboard page, Observations, scoring Patterns into noticed, suspected and closed, unmatched Patterns with the matching command, and the ready gate; `docs/pattern-pipeline/README.md` says how these fit together._

**Pattern Catalog**:
The human-written, versioned set of Pattern Types the Companion may look for in a User. It is the only source of Patterns that can be shared: the model reads what Users say into it and never adds to it. Unlike Platform Settings it lives with the code and changes only through a reviewed change and a deploy, so every Observation can keep the version it was tagged under and history can be scored again; Admins read it on the Dashboard but don't edit it there. The numbers that apply to every Pattern Type (score bars, situations needed, fading, limits) are Platform Settings.
_Avoid_: Codebook, ontology, rule set

**Pattern Type**:
One entry in the Pattern Catalog: a way of acting written as "in this situation, the person tends to do this, apparently to protect or get that", in our own words and never in clinical language. It has a stable ID that is never reused and a version: any change gives it a new version, and every version loaded is kept as it was. It has a definition; signs for it, each weak, moderate or strong and marked with the part it shows (the situation, what goes on inside, or the behaviour); signs against it; its look-alikes, each with what tells the two apart (a pair is always named by both Pattern Types, each saying the difference from its own side), including what anyone would do in that situation (in words, and where it can be, as situation tags, so code can tell which Observations carry no weight); exclusions (times it must not be scored or shared, e.g. grief or a recent job loss); the approved wording for sharing it and for its Prediction; its own numbers; and one of five areas (conflict, approval, control, achievement, relationships). It is draft, approved (with who approved it and when) or archived: a Pattern of a draft Pattern Type gathers evidence but is never ready, and an archived one is no longer looked for.
_Avoid_: Hypothesis type, construct, trait, codebook entry

**Observation**:
One piece of evidence for or against a Pattern, taken from something a User said: their exact quote, a line on what was going on (the Companion's wording, shown apart from the quote), the day, its Life Thread if any, who it was about, and tags the model picks from fixed lists: the Pattern Type and the sign it matched, for or against, the relationship (partner, family, friend, acquaintance, colleague, stranger), power (above, equal, below), setting (home, work, social, online), the other person's stance (supportive, neutral, hostile), and the kind of evidence (a real story, a habit they report, an answer to a "what if", their own opinion of themselves, weighted in that order). One the model can't place between two look-alikes names both and is unclear, counting for little toward each; one whose tags match what anyone would do there carries no weight, and nor does one said while an exclusion of its Pattern Type applied whose evidence is ignored (e.g. grief). The model also says which exclusions apply to the User now, from their open Life Threads and latest Day Summaries, and marks an Observation that touches a topic on the Admins' ruled-out list, with whether the User raised it themselves: a Pattern resting on one they didn't raise is never ready. Tagged when a Conversation ends, after its Life Threads. Code keeps only those whose Pattern Type and sign exist, whose quote is word for word in the User's own texts and whose tags come from the lists. It is User Memory: the quote stays after Message Retention deletes its message, and Users see every kept quote with its line and day under "Things you said that Zeph kept", with no Pattern named, and can delete it, which scores its Pattern again. None is kept for a User until they have pressed "Got it" on the Dashboard notice saying Zeph now keeps some of their words.
_Avoid_: Evidence item, tag, signal, data point

**Thought Experiment**:
A made-up scenario the Companion asks a User to think through ("you can tell a close friend they're making a mistake and risk a cold week, or say nothing…"), written to tell two look-alike Pattern Types apart. Managed by Admins on the Dashboard: each has its wording, the two Pattern Types it separates, how sensitive it is, whether it is a starter and whether it is on; a check on save flags leading wording; one is archived, never deleted. It is asked as a Curiosity, in chat or as a Check-in, in its own words. Its answer is an Observation of the "what if" kind, so it counts for less than something that happened. Starter ones are broad and go to a new User in their first Conversations. *(Built 24 Nov 2026: the Admin page, a first set of 31 from the seed (each new seed key added once; an edit or archive is never undone by the seed), the leading-wording check (a word list; "Save anyway" saves it), and the Thought Experiment way of an Exploration: for an unclear story, code picks one for the look-alike pair with the most unclear stories, on, not archived and never put to that User, at most an Admin-set number per Pattern in 7 days. Switching one off or archiving it closes the Curiosity waiting to ask it. Starter ones go to a new User, built 25 Nov 2026 with Familiarity; a "what if" answer alone never makes a Pattern suspected. Guide: `docs/thought-experiments/README.md`.)*
_Avoid_: Probe, quiz, test, hypothetical

**Exploration**:
The Companion's ongoing effort on one of a User's Patterns: what it still needs to learn (an unclear story to settle, a part of their life it hasn't seen, or a counter-test: a situation where the Pattern says it shouldn't show up), each try (which Curiosity, when, and whether what came back was useful, vague or brushed off), and what to try next and not before when. A try that gets nothing useful leaves the need open, and the Companion comes back later a different way, least pushy first: a follow-up on a story they tell, "would it have gone differently with…", a Thought Experiment, "this week, notice when…". It is never worked on two Conversations in a row, rests after an Admin-set number of tries with nothing, and wakes on new evidence. Written and moved by code. Users don't see Explorations; Delete My Data and Account Deletion remove them. *(Built 24 Nov 2026, behind the Feature Pattern exploring, which works only while Pattern noticing works: a suspected Pattern gets one; its needs are worked out from its Observations, unclear stories first, then a part of life (home, work, with friends) not seen while another is, then a counter-test; a try's outcome is decided by code from how the User took it and whether new evidence came; a try aimed at an unclear story whose answer settles it is tagged clear at Conversation end. Asking to drop one rests it at once. Deleting the story a try aimed at deletes that try with its Curiosity. Thought Experiments are a way since 24 Nov 2026, for unclear stories only.)*
_Avoid_: Investigation, case, probe plan

**Agenda**:
A User's active Explorations, at most an Admin-set number at once, ranked by code. The Reply Plan sees it on every reply, with each Exploration's earlier tries, so the Companion always knows what it is trying to learn and what it has already asked. *(Built 24 Nov 2026: ranked by score, highest first, then oldest; kept at Conversation end while Pattern exploring and Curiosities work; not shown while the User is struggling. A Move that asks a question, such as Get curious, is given its open needs in plain words.)*
_Avoid_: Backlog, queue, to-do list

**Prediction**:
The one thing a User is asked to watch for in their own life when a Pattern is shared ("next time your mum asks for something you'd rather not do, notice whether you say yes before you've decided"), from its Pattern Type's wording, kept as the Companion put it to them. After an Admin-set wait the Companion asks how it went, as a Curiosity; one not asked within a longer Admin-set time is dropped and counts nothing. What the User reports is read by the model as came true, didn't or hasn't come up, and is the strongest evidence there is, for or against: enough that came true confirm the Pattern, and "hasn't come up" counts nothing and is asked again later. A shared Pattern always has one to watch for: when the last is settled or dropped, the Companion offers a new one. *(Built 25 Nov 2026: the wait starts at 7 days, the drop at 21, and 2 that came true confirm.)*
_Avoid_: Homework, task, challenge

**Familiarity**:
How well the Companion knows a User, worked out by code from counts (Conversations, Life Threads, Observations from real stories, Pattern states) against Admin-set bars, each time a Conversation ends: new (it asks starter Thought Experiments and broad questions), getting to know (the Agenda takes over, with questions aimed at their real experiences) or knows well (at least one Pattern shared or confirmed: it follows up Predictions and narrows Patterns). The Reply Plan is told it on every reply; Admins see it for each User. *(Built 25 Nov 2026. The bars start at 5 Conversations, 3 Life Threads and 0 Observations from real stories, or a first suspected Pattern. It follows the counts, so it can go back, and Delete My Data makes a User new again. Starter Thought Experiments go to a new User while Pattern exploring works: at most 4 in the 14 days after sign-up, at most 1 a Conversation, all Admin-set.)*
_Avoid_: Stage, level, onboarding stage

### Understanding

**Need**:
What the User wants from the Companion right now (e.g. to be heard, to think it through, advice, accountability on a Goal, or to get something done, like changing a setting or forgetting something). Being heard is for a User who is letting out something painful and staying on it; a hard thing mentioned in passing (tired, a long day, a small annoyance) is an update, just chatting. Before each reply the Companion picks the one that fits best, fresh for every message. Managed by Admins: each has a name, when it fits, and how to reply, and only the picked Need's "how to reply" shapes the reply. One fallback Need ("Ask more", to start) is used when it isn't clear, or when the Understanding or Reply Plan can't be made; it can be edited but never deleted. Any other Need can be deleted; Reply Plans that named it keep the name. No two Needs share a name, ignoring case, and Admins set the order they are listed in. Each Need sets the tone and stance of the reply (e.g. "listen, don't fix") and lists the Moves that never go with it; what the Companion actually does is its Moves. Each Need also says how Curiosities are treated while it is picked: asked by default, tested lightly, only if they fit, or never. Changes reach the next reply.
_Avoid_: Intent, mode, mood (mood is how a User seemed in a Day Summary)

**Move**:
What the Companion does to help in a reply (e.g. Calm, Ground, Reframe, Mirror, Suggest, Plan steps, Push, Research, Get curious), as opposed to the Need, which is what the User wants. Each reply has a lead Move and at most one supporting Move, or none (just responding), picked in the Reply Plan from the Moves the picked Need allows, in the light of the Moves already made in the Conversation and the User's Move Outcomes. The Reply Plan may also hold a next Move in mind, with why, which the next Reply Plan follows or drops (a fallback Reply Plan, used when the model fails, does neither); it may be one the picked Need rules out, since the User may need it later, but must be one some Need allows and that can be offered to the User now; over a Conversation this makes a sequence (e.g. hear them out, then reframe, then plan steps). Get curious is how the Companion gets to know a User: one natural question about something they just said, to learn something new, go deeper, or check something it isn't sure of, never in the same reply as another question. A Move may unlock tools and may need a Feature (Research needs Web Search); one whose Feature doesn't work for the User, or whose limit is used up for the day, is never offered to the Reply Plan. A Move marked "asks a question" (Get curious is) is never made in two replies in a row, and is dropped from a reply that also asks why or raises a Curiosity: the other question wins, the dropped Move isn't recorded as made, and a supporting Move never moves up to lead in its place. Managed by Admins: each has a name, when it fits, how to do it, the Feature it needs, if any, and whether it asks a question; no two Moves share a name, ignoring case, and Admins set the order they are listed in. A deleted Move is never picked again and is removed from every Need's rule-outs; Reply Plans and Move Outcomes that named it keep the name. Changes reach the next reply.
_Avoid_: Strategy, technique, action, intervention

**Move Outcome**:
What the Companion learned about how one Move went for a User: the Move, whether it led or supported, the situation, how the User felt, whether it helped, didn't or was mixed, why, and when. Kept when a Conversation ends, as part of User Memory, so the same Move can be known to help in one situation or mood and not in another. Before each reply the Reply Plan is shown, with their days, the User's own ones whose situation and feeling are closest in meaning to their last few messages, up to an Admin-set number (starting at 3) and only those past an Admin-set closeness bar; it reads them knowing a Move that helped before may not help now. They are used even while User Memory is off, which only stops new ones being kept. Users see them under "What helps you" and can delete them; Admins see only how many a User has.
_Avoid_: Feedback, rating, result

**Understanding**:
The Companion's private sense of what a User just said, made before it replies, and only that: it decides nothing about the reply. Read in the light of the whole Message and Conversation, it says what they said and mean, when it came (in their time zone), how they feel and how strongly, what they want, whether it knows why they feel that way, whether they are struggling and whether they asked to see one of their photos. For how they feel and what they want, it keeps apart what they said in their own words, what the Companion only reads from how they said it, and what is unclear: the reply acts on what was said, holds what was read lightly and never names it as fact, and checks what is unclear when it matters rather than guessing. Every Message gets one, however short, since a short one ("yep") is often the one that matters. Each Understanding sees the earlier ones in the same Conversation, so the Companion knows how the User's mood is moving. Users don't see Understandings. Removed with the messages it was made for.
_Avoid_: Analysis, classification, note, intent detection

**Recall**:
Bringing to mind, between the Understanding and the Reply Plan, everything from a User's memory that might matter to what they mean: Life Threads, Patterns, Memory Items, Knowledge passages, older Day Summaries, Move Outcomes and due Curiosities. It is wide on purpose, found by meaning however old, and decides nothing: the Reply Plan picks what the reply uses. Whatever came to mind stays in mind until the Conversation ends.
_Avoid_: Retrieval, memory search, lookup

**Read**:
The Companion's honest view of what is really going on with a User, formed before each reply from its Outlook, the Understanding and what it remembers, above all their Patterns (e.g. "the PM, the project and the impatience with their mum are the same thing: when something grabs them, everything else goes quiet"). It is the Companion's own view, never stated as fact. Having one is not optional; saying it is. The Reply Plan has the reply say it only when there is room (the User isn't mid-vent, in crisis or just chatting lightly; a vent is heard first and the Read can come once it is spent), it is worth saying (it adds something they haven't said, joining things or giving a real view on their question, not their words handed back), and it is not a repeat (never the same Read twice in a Conversation; a Pattern the User pushed back on waits an Admin-set time before it is offered again). When the User asks for Zeph's view ("thoughts?", "don't you have opinions?"), it gives its deepest Read straight away, not advice it already gave. How gently it is said follows the Outlook and how the User is feeling. The Read is free: it is a view of this situation and may think with any Pattern in mind, but naming a Pattern as who the User is happens only when a ready Pattern is shared. Each User sets how direct the Companion is with its Read (gentle, balanced to start, or direct), on the Dashboard or in chat: how soon and how plainly it is said, never whether a Pattern is ready, and not while they are struggling.
_Avoid_: Opinion, insight, take, analysis

**Reply Plan**:
What a reply is built from, decided after the Understanding and before the reply is written: the Read, the Need, the lead, supporting and next Moves, and what the reply uses from everything that came to mind (which Life Threads to bring up or leave alone and why, a Pattern, a Curiosity, Knowledge, a Shared Photo, and whether a Woven-in Check-in fits at all). Everything optional is weighed here against what the User needs right now; nothing reaches the reply as a separate order. It also says in a line where the Conversation is now (e.g. "venting, nearly spent", "asking for a view"); each Reply Plan sees the earlier ones in the Conversation, so the Companion knows when to hold and when to push rather than starting fresh with every Message. When their mood stands out and the Understanding doesn't know why, the plan may have the reply gently ask, in the Companion's own voice, but never while they're venting and never twice in a row. When a Day Summary isn't detailed enough, the Reply Plan can read a past day's messages word for word, while Message Retention still keeps them; what it read goes to the reply with what the Companion remembers. Past retention there are none, and the Companion answers from the Day Summary without claiming the User's exact words. Users don't see Reply Plans; what is learned from them (their User Portrait, Life Threads, Patterns) is theirs to see and delete. Removed with the messages it was made for.
_Avoid_: Strategy, decision, intent

**Curiosity**:
Something the Companion wants to ask or talk about with a User later, worked out when a Conversation ends from what it knows about them, including a next Move it still had in mind when the Conversation ended and never made, since an earlier one was already followed or dropped (e.g. "did they decide what 'done' means for internal testing?", "how did the presentation go?", "they've seemed low on Sunday nights, wonder why"). Every Curiosity has an aim: something an Exploration still needs, a Prediction to follow up, a commitment to follow up, a look-back (how something that was coming up went, or how they see something now), a guess to check, or where they've got to on a next Move never made; one with no aim is never made. Code writes the ones from the Agenda and ranks all of them; the model only words them, and a Thought Experiment is asked in its own words. It is saved, not sent: when the User next talks to the Companion each Need says, as Admins set it, whether Curiosities are asked by default (the Reply Plan asks one or says why not), tested lightly (at most one light opener in a Conversation, asked in passing so it is easy to let go; Just chatting, to start), asked only if they fit, or never; one the Reply Plan picks is part of the plan the reply follows, not an optional extra, and one Check-in Kind starts a Conversation with one: it is marked raised once that Check-in is sent, and a reply to it counts as this Conversation's raised Curiosity. Some hold a guess: something the Companion suspects about the User but isn't sure of (e.g. "their mum lives in Singapore"), with how sure it is; a guess is never stated as fact, only checked gently, and is closed once the User answers, what they said being kept as a Memory Item when the Conversation ends. A commitment the User made becomes a follow-up ("did you get to call your mum?") not before the day after it was due. Something the User vented about while the Companion only listened becomes a look-back: a gentle question about how they see it now, asked no sooner than the next day and treated as at least medium sensitivity. Each has what to ask and why, a "not before" day (or anytime), how sensitive it is, and whether it is waiting, was raised (and how the User took it) or is no longer relevant. Curiosities are internal: they aren't User Memory and Users don't see them, but Delete My Data and Account Deletion remove them, and deleting the Memory Item or Life Thread one came from removes it too. Before each reply the Reply Plan sees the waiting ones whose "not before" day has come in the User's time zone, with how many were already raised in this Conversation, and may bring up as many as Admins allow per reply (one, to start); none are offered once the Conversation has raised as many as Admins allow, and never while the User is struggling (that rule is fixed, not a setting). While Admins hold Curiosities back from a reply that asks why they feel as they do (on, to start), such a reply asks no Curiosity too and it stays due; with that off, the reply asks why first and the Curiosity after it. One brought up is marked raised when the reply is sent; how the User took it is read by the next Reply Plan, if the reply really asked it, and judged again when that Conversation ends. Over the waiting limit, the oldest waiting ones are closed. While User Memory is off no new ones are made and no reactions are recorded, and waiting ones are still used. It is a Feature, on for everyone to start; when it doesn't work for a User none are made or raised, and none are deleted. Curiosities are spaced by an Admin-set fewest replies between two, counted across Conversations; a follow-up on a story the User is telling right now (a Move that asks a question, such as Get curious) doesn't count toward the limits and has its own cap per Conversation. After an Admin-set number of brush-offs in a row (asking to drop one counts) none are asked for the rest of the Conversation and the spacing doubles for an Admin-set time from the last brush-off; one engaged answer ends that. One they asked to drop is never asked again, and no new one is made on that topic unless they bring it up. Admins set how many are raised per Conversation and per reply, whether one is held back from a reply that asks why, how many Curiosity Check-ins a User gets per week, and how many can wait at once. *(Target design agreed 24 Nov 2026, see `docs/pattern-pipeline/README.md`. Built 24 Nov 2026: the aims a model writes, the per-Need field, a picked Curiosity as part of the plan, testing lightly, spacing and backing off, and the Agenda's aimed Curiosities, written by code, offered first and only while Pattern exploring works, never seen or closed by the Curiosity keeping step. Built 25 Nov 2026: Prediction follow-ups, written by code with a first and a last day, offered first and only while Pattern sharing works.)*
_Avoid_: Probe, question bank, prompt, talking point

### Knowledge

**Knowledge**:
The curated library of philosophy, psychology and mindfulness material the Companion draws on, made of Knowledge Documents. Shared by all Users; never about any one User. The Companion brings it in only when it genuinely fits the message, lightly and in its own words, never as a lecture. When the User asks about a practice or teaching in the passages it was given, or where one comes from, the reply answers from them (their steps, or their title, source and tradition) rather than from what the model remembers elsewhere. The Reply Plan decides whether any Knowledge Document fits, from each one's "when it helps", and if so picks the documents from the Ready ones it is shown, plus a search phrase; only passages from those documents that are close enough to the phrase (an Admin-set bar) go into the reply. Most messages, such as a vent or small talk, get none. It is a Feature: when it doesn't work for a User, no Knowledge goes into their replies and none is offered to the Reply Plan.
_Avoid_: Wisdom base, corpus, content

**Knowledge Document**:
One text in the Knowledge library (text, Markdown or PDF), with a title, a source or author, a tradition, and a "when it helps" description (drafted by the Companion when it is made ready without one, naming the practices it covers; a failed draft leaves it blank for an Admin to write) that the Companion reads to decide whether the document fits what the User needs; Admins can change those details at any time and replies use them straight away. It is Pending until it is made ready, then Ready (used in replies) or Failed (with a reason; an Admin can retry it). Only Ready documents are ever used. Its text, read from its file, is what replies draw on; Admins can view and edit it on the document's page, and an edit makes the document Pending until it is re-indexed (it is then marked Edited, as it no longer matches its file word for word). Replacing its file keeps the document, its details and when it was added, reads the new file's text and clears Edited. Deleting one removes it from replies at once.
_Avoid_: File, article, resource

**Starter Knowledge**:
The Knowledge Documents loaded on first run, when the library is empty: public-domain texts and the owner's own summaries, mindfulness first. After that the library is Admin-managed, so a deleted starter document never comes back.
_Avoid_: Default knowledge, seed content

### Web

**Web Search**:
The Companion looking something up on the web while it replies — searching, or reading a page — when the Conversation needs a fact it doesn't know well, or when the Research Move does the legwork for the User (finding and comparing options against what they need). Queries carry only the general topic and practical requirements (e.g. a budget), never the User's personal details, and a reply that uses web information says where it came from. It is a Feature, so Admins can turn it off; when it doesn't work for a User, the Companion tells them plainly it isn't available on their account.
_Avoid_: Browsing, internet lookup, googling

**Web Search Limit**:
The most Web Searches the Companion makes for one User in a day, set by Admins; each search and each page read counts as one. The day is the User's own, so it resets at midnight in their time zone. Once it is reached the Companion replies without the web until the next day; when a lookup would have helped, it tells the User plainly it can't look things up again until tomorrow and answers from what it knows, never claiming it searched.
_Avoid_: Search quota, web budget

### Usage

**Daily Message Limit**:
The most Messages a User can send the Companion in a day, set by Admins and meant to be generous; several texts in a row are one Message. The day is the User's own, so it resets at midnight in their time zone. The Safeguard still checks every text first: a crisis always gets the Crisis Reply and never counts toward the limit. Over the limit, the Companion answers with the Limit Reply instead of a real reply until the next day. Check-ins don't count toward it, but once a User has used it up, they get no more Check-ins that day (see Skipped Check-in).
_Avoid_: Quota, rate limit, message cap

**Limit Reply**:
The short, in-character message (e.g. "I'm wiped for today, talk tomorrow?") sent instead of a reply once a User is over the Daily Message Limit. Its wording is set by Admins.
_Avoid_: Error message, limit notice

**Usage**:
What each User used on each of their days, as counts only: messages, chat model tokens read and written (for everything the Companion does for them, Check-ins included), and Web Searches, plus whether the Daily Message Limit or Web Search Limit turned anything away that day. Admins see it; it never holds message content.
_Avoid_: Billing, costs, activity log

### Privacy

**Recent Messages**:
Every message between a User and the Companion from the last 24 hours (Admin-set), across Conversations and across midnight, word for word. The Understanding, the Reply Plan and the Reply all see them, so "as I was saying…" works after a break; a later Conversation among them is marked with when it started, and the Reply Plan also sees where the previous one was when it ended. On a very heavy day the oldest messages past an Admin-set cap are left out and their Day Summary stands in, to cap cost. Not to be confused with a Check-in's reply window.
_Avoid_: Reply window, history, context window

**Message Retention**:
How long a User's raw messages are kept, set by Admins in days. Older messages are deleted automatically; Day Summaries, Memory Items, Shared Photos and Observations (with the User's quotes in them) stay until the User deletes them, and Users are told so plainly.
_Avoid_: Data retention, TTL, history limit

**Delete My Data**:
A User's choice, on the Dashboard or in chat, to wipe their messages, User Memory, Personal Stickers, Check-in history and Telegram Connection after confirming (on the Dashboard in a confirm dialog, in chat by sending a confirmation word), along with everything the Companion keeps about them that they don't see (Understandings, Reply Plans, Curiosities, Explorations and Patterns not yet shared). Users are told it removes everything, private notes included. In chat the confirmation must be their whole next Message, the word sent on its own; anything else cancels it, and they are told why. Their account stays, so they can start fresh. The Admins' Feature choices for them stay too, since they are Admin settings, not the User's data.
_Avoid_: Reset, clear history, wipe

**Account Deletion**:
A User's choice, made only on the Dashboard, to remove everything Delete My Data removes plus their account itself and the Admins' Feature choices for them. It can't be undone, and the last Admin can't do it. Once confirmed it always finishes: the User is signed out at once, and if their sign-in account can't be removed right then, it is removed later without them doing anything. Anything they create by signing in again before then is removed with it.
_Avoid_: Close account, deactivate, unsubscribe

**Model Call Log**:
The Admins' record of every model call the Companion makes, grouped by what it was for: a Message, a Check-in, or the work done when a Conversation ends. For every User it holds no content: which steps ran, the model and whether it thought first, tokens, time taken, errors and the shape of each decision, never its words: for an Understanding, the mood's intensity, whether its cause was known, whether the User was struggling and how many past look-ups it asked for; for a Reply Plan, the Need picked, the lead, supporting and next Moves, and how many Life Threads it was reminded of, brought up (led with or woven in), left alone and held back, whether it formed a Read and said it, and how many Check-in Kinds it could weave in and which it chose; for the check on a Woven-in Check-in, its Kind and whether the reply brought it up; when either couldn't be made, the fallback it used. Full content (what the model was given, what it answered, its tool calls and its reasoning) is kept only for Admins' own chats and Evals. Removed with the User's messages.
_Avoid_: Trace, debug log, LLM log

### Quality

**Eval**:
A measurement of how the Companion behaves with the real LLM, run on demand in an Eval Run and never in the normal checks, because it costs money and its results vary. There are Safeguard, Persona, Knowledge, Settings, Photo description, Understanding, Move Outcome, Day Summary and Tagging Evals; a Tagging Eval gives a made-up ended Conversation and the Life Threads it touched, runs the real tagging step alone on it with the whole Pattern Catalog, and passes only when the Observations code keeps are exactly the ones expected (Pattern Type, for or against, unclear, situational), showing each one kept and each one dropped with why (no Judge; what it can and can't show is in `docs/pattern-evals/README.md`); a Day Summary Eval gives a made-up day of messages (split into Conversations where it went quiet), runs the real Day Summary step alone on it, and has the Judge answer questions about the facts, the feelings and what the Companion offered from the Summary alone, never seeing the messages or the answers expected, then mark each answer against the answer expected, passing only if every answer matches; a Settings Eval checks that plain-words requests make exactly the right Chat Setting Change, or none, and an Understanding Eval gives a made-up User a User Memory and checks each Message on the step that owns each check, so a failure says which job went wrong: the Understanding (whether the User is struggling, whether the cause is known, past look-ups, and feelings and wants kept as said only when put in words), Recall (Life Threads found) and the Reply Plan (whether a Read was formed and said, the Need picked, the lead, supporting and next Moves, Life Threads brought up or left alone, Curiosities, asking why, Knowledge, a Woven-in Check-in), and a Move Outcome Eval gives a finished Conversation (its messages and the Moves each Reply Plan made), runs the real Move Outcome keeping step on it and checks the Move Outcomes kept, their results and why, and the keeping call's time and tokens. Each one goes through the real reply path (or, for Move Outcomes, Day Summaries and Tagging, the real Conversation-end step) with the Platform Settings, Needs and Moves Admins have set, changed only by a Variant's Setting Overrides. Its made-up Users, messages and documents are kept fully apart from real Users and their data; an Eval never messages a real chat or searches the real web. An Understanding case may turn Web Search off for its User, and may give made-up web pages that its searches find, so Research is tested for free; its made-up User Memory may include Move Outcomes, found by closeness as real ones are.
_Avoid_: Test, benchmark

**Eval Case**:
One situation an Eval checks, such as one labelled message for the Safeguard Eval or one made-up User and their Messages for the Understanding Eval, with what is expected to happen. Each has a key, such as `reminded-of-sister`, unique across all Evals. Admins add, edit, duplicate and archive Eval Cases on the Dashboard; the starting ones come from seed files, and a seed never overwrites an edited case or brings back an archived one. Archived cases are kept so past Eval Runs still show them, and can't be changed; duplicating one starts a new case like it. A photo case's images are kept with the cases, and an image once kept never changes.
_Avoid_: Test case, fixture, scenario

**Eval Run**:
One go at some Eval Cases (whole Evals or single cases), started by an Admin on the Dashboard or from the terminal. Before it starts, Admins see an estimate of its tokens and cost. It is Queued until it can start (one runs at a time), then Running, and ends Finished, Cancelled, Interrupted (it stopped unexpectedly; it is never retried by itself) or Stopped over limit (it crossed the Eval run token limit). Cancelled and Stopped over limit take effect after the case under way (or between the Messages of an Understanding case, which then ends as an Error) and keep every finished Case Result. Each Eval Case gets a Case Result as soon as it is done, so Admins watch them come in. A run keeps what it used (the Platform Settings, the Needs, the Judge's settings and each case as it was), so later changes never alter its results. Runs started from the terminal are hidden from the run list unless an Admin chooses to see them. Runs are kept until an Admin deletes one.
_Avoid_: Eval job, test run, batch

**Variant**:
One set of Platform Settings an Eval Run tries: the live ones, or the live ones changed by its own Setting Overrides. A run has one to three Variants; each runs every chosen case the same number of times (its Repeats), so they can be compared side by side. A run goes case by case: each try of a case runs on every Variant before the next try, and every try before the next case, so a run that stops early still compares fairly. Every try starts from fresh made-up data. The Judge is the same for every Variant in a run. Re-running a run's failed cases keeps its Variants and Repeats.
_Avoid_: Arm, configuration, experiment

**Setting Override**:
A change to one Platform Setting (a prompt, a Need, a Move's text, a model, thinking on or off, a limit) that applies only inside one Variant of an Eval Run. It is held to the same checks as a save on the settings pages, and a Need or Move can be changed but not added or removed (a Move's needed Feature and a Need's ruled-out Moves stay as they are live). It never changes what real Users get, unless an Admin makes it live. A Variant changing a Need or Move deleted before its run starts ends its cases as Errors.
_Avoid_: Draft setting, temp setting

**Make Live**:
An Admin's choice to apply a Variant's Setting Overrides to the live Platform Settings, only on a Finished Eval Run and once per Variant. If a setting's live value changed since the run started, the Admin sees the value then, the value now and the override, and confirms or leaves out each such setting; the others apply straight away, through the same saves as the settings pages. The run shows who made it live, when, and what was applied or left out.
_Avoid_: Promote, deploy, publish

**Case Result**:
How one Eval Case went in one Variant on one try: Pass, Fail (the Companion behaved wrongly) or Error (it couldn't be checked, for example the model didn't answer), with the Judge's reason for each rule, the tokens, the time and every model call's full content (its trace; the Judge's own calls aren't in it). Traces are Eval-only and never show in the Model Call Log. Errors don't count as fails. Re-running a run's failed cases includes its Errors.
_Avoid_: Test result, score

**Model Price**:
What a model costs in Singapore dollars per million tokens in and out, set by Admins and used for Eval Run cost estimates and totals. A run is priced at the Model Prices it started with. A model with no price shows tokens only, marked "no price set", and never blocks a run. Admins set the price per model name, whichever provider runs it; for DeepSeek models it is the highest price DeepSeek charges, so real costs are lower. The price OpenRouter reports is not used.
_Avoid_: Rate, tariff

**Missed Crisis**:
A real crisis that the Safeguard lets through as "none". Any Missed Crisis fails the Safeguard Eval.
_Avoid_: False negative

**False Alarm**:
An everyday message that the Safeguard treats as a crisis, such as "this traffic is killing me". False Alarms are reported but are accepted in small numbers.
_Avoid_: False positive

**Judge**:
The LLM that marks a Persona, Knowledge, Understanding, Move Outcome or Day Summary Eval: for each rule it says whether the replies keep it (for a Move Outcome Eval, whether a kept Move Outcome's situation, feeling and why keep it), for a Knowledge Eval it says which version of a document a reply used, and for a Day Summary Eval it answers each question from the Summary alone, then marks each answer Match or Miss against the answer expected. It always gives a reason. It can be wrong. Admins set its model, thinking and prompts; a Variant's Setting Overrides never change it.
_Avoid_: Grader, evaluator
