# 01 — Understanding: the Companion works out what the User needs before replying

Status: needs-triage

## Idea (from the User, during the architecture grilling, 14 Nov 2026)

Chatting with the Companion still feels slightly empty. Today it goes straight from "here is everything" to one reply call. It should first try to understand the User and their intent, then decide its next step:

- Should it ask more to understand?
- Does it have memories about the User that make the reply meaningful?
- Is this something the User keeps coming back to, and what worked for them before?
- Is any Knowledge relevant, and should the Companion bring it up?
- Or does the User simply want to rant?

Added when revisiting, 14 Nov 2026:

- Does the Companion understand the context of the Conversation?
- Is Knowledge search actually useful? It embeds only the newest message (`knowledge_retrieval.py:99`), so "yeah, exactly" finds nothing. Searching with the last 2–3 User messages joined would find better passages.
- Does the Companion remember older Conversations? Only the 3 newest Conversation Summaries go into a reply; anything older is lost unless it became a Memory Item. Raise the number, or search old summaries by meaning (like Knowledge), so "how did that job interview go?" works weeks later.
- Replies use `deepseek-chat`. Try a stronger model for replies only and compare.
- Follow up on things the User mentioned. The Companion could look back at "big presentation Thursday" and check in about it afterwards — the "friend who remembers" feeling from `ABOUT.md`.
- Show typing on slow replies. Typing shows when the message arrives, but Telegram hides it after ~5 seconds, while memory picking, Knowledge search, the reply call and Web Search can take longer. Send "typing" again every ~4 seconds while the reply is being written.
- Wait for the User to finish typing before replying (biggest win). People send 2–3 short texts in a row; today each gets its own reply (`incoming_messages.py:239`). Only Albums are grouped. Wait a few seconds after the last message, then answer them all in one reply, reusing the Album wait idea.

The Companion is not just a chat companion. It helps Users understand themselves, acts as an accountability partner for their intentions, goals and ambitions, and helps them make sense of their life. Think life coach, therapist, accountability partner and close friend who knows them well.

## What we noticed in the code

- No thinking step: `ResponseComposer.compose` is one model call (with tools).
- Memory is picked by Memory Category, before the Companion understands the message.
- Knowledge search embeds only the newest message.
- Nothing looks for patterns across Conversations.

## Decisions (grilling, 14 Nov 2026)

- **Scope.** This PRD covers how a reply gets its context and uses it: working out what the User needs before replying, picking memory after that, finding older Conversation Summaries by meaning, searching Knowledge with recent messages, and bringing up past things naturally in the live Conversation (memories, Goals, past Conversations, the way a friend is reminded of something — irregular, not robotic). That last one is not Check-ins: Check-ins are the Companion starting a Conversation.
- **Shape: understand first, then fetch, then reply (option A).** A cheap understanding call replaces the memory-picking call. It writes a private note (what the User needs, what to bring up or leave alone, what to look up). Code fetches what the note asks for, and the reply call gets the note plus that context. Picked over giving the reply model lookup tools (option B) because it is steady in speed and cost, always considers the past, and is easy to test and tune. **Future:** the User values flexibility, so a hybrid is likely later — A plus one or two lookup tools (e.g. search past Conversations) for the rare deeper dig. Keep the design open to that.
- **What the User needs: one pick from an Admin-managed list, plus a sentence of nuance.** Starting list: Be heard, Think it through, Advice, Accountability, Ask more, Just chatting. Admins can add, edit and retire them on the Dashboard with no redeploy (ADR-0004), like Check-in Kinds. This is the core of the product and humans must be able to steer it any time. A fresh pick for every message, since needs shift mid-Conversation.
- **Need fields and rules.** Glossary term **Need** (added to `CONTEXT.md`). Fields: name, "when it fits" (read by the understanding call to choose), "how to reply" (given to the reply call only for the picked Need). Admins can delete any Need except one fallback ("Ask more"), which is used when the pick is unclear and can be edited but not deleted. Nothing stores a link to past picks, so deleting is safe. With the fallback always there, the list is never empty.
- **The understanding call returns a fixed-shape form** (need, nuance, bring up, look up). The model only fills it in; the code reads it and runs any lookups. That keeps option A's fixed order.
- **Knowing the User: layers.** Memory Items (facts, picked by category in the same understanding call), Conversation Summaries (newest few always; all searchable by meaning for deliberate lookups), **Life Threads** (new: ongoing stories, the unit the Companion is *reminded* by) and the **User Portrait** (new: a living whole picture, always included, rewritten when a Conversation ends). Terms added to `CONTEXT.md`.
- **Being reminded is the heart of this feature.** When the User says "my sister's wedding is next week", the Companion should be able to lead with "how are things with Mei now?", from a falling-out 9 months ago, not just answer the surface topic. On every message the code automatically finds Threads by person or thing named (direct match) and by meaning (the last 2–3 User messages joined), open Threads first, with no age limit. These go *into* the understanding call, which decides: lead with it, follow the moment, or leave it (timing: not when they need to be heard on something else or are struggling; never robotic, so no repeat within a Conversation and not a callback every message). Summaries searched by meaning were rejected as the reminder unit: one Summary blends several topics, so matches are weak.
- **Follow-ups on things mentioned** ("presentation Thursday") are open Threads with a date, brought up naturally once the date has passed.
- **Order per message:** reminded search (no model call) → understanding call (Portrait, newest Summaries, Goals, Memory Category names, reminded Threads, this Conversation's earlier understanding records) → fetch deliberate lookups and Knowledge → reply call. Two model calls per reply, as today. Writing Threads and the Portrait adds work when a Conversation ends, in the background.
- **Tracking what was said:** (1) each exchange's understanding is saved with the messages (deleted with them by Message Retention and Delete My Data; the Need is saved by name, so deleting a Need stays safe); (2) each Thread records when it was brought up and how the User took it (engaged / brushed off / asked to drop it); (3) Summaries record what the Companion offered and how it landed, feeding the Portrait's "what helps / what doesn't".
- **Understanding record (term in `CONTEXT.md`).** Saved for each answered message. User side: when (their time zone, weekday), mood right now, intensity (low/medium/high), whether the cause is known, Need picked plus nuance, Threads touched. Companion side: what it brought up and how (led with it / wove it in), what it looked up and whether anything was found, what it was reminded of but left alone and why. Used by the next Understanding in the Conversation (mood arc, "already asked about Mei") and when the Conversation ends (Summary mood arc, how each bring-up landed on Threads, Portrait patterns).
- **Probe when the cause is unknown.** When the mood stands out and the cause is not known, the Companion gently asks in its own voice ("someone's buzzing today haha, what's going on?"), but not while they vent and not twice in a row. The Portrait keeps open questions ("low on Sunday nights, not sure why") to explore when the moment is right.
- **Curiosities (term in `CONTEXT.md`), in this PRD.** Things the Companion wants to ask a User later, written at Conversation end (not a periodic job: nothing new is learned between Conversations, and a timer over all Users wastes calls; dates are handled by a "not before" day). They replace the Portrait's "open questions". The Understanding call sees waiting Curiosities whose day has come and decides whether to raise one. Internal: not User Memory, not shown to Users (User's call), but removed by Delete My Data / Account Deletion and when the Memory Item or Thread they came from is deleted; no new ones while User Memory is off. A Feature (for future tiers) with Admin-set limits: raised per Conversation (start 1), Curiosity Check-ins per week (start 1), waiting at once (oldest dropped). New Check-in Kind "something I've been wondering": fixed behaviour like the photo Kind, only for a User with a Curiosity whose day has come. Platform-wide values for now; per plan when tiers exist.
- **Clear messaging about memory off vs delete.** Users must understand: User Memory off never deletes anything, it only stops learning; Delete My Data removes everything about them, private notes included. Gaps to fix: the Onboarding consent text says "everything I remember is listed on your Dashboard", which is no longer true, so add an honest line about private notes; the in-chat memory-off confirmation gets a fixed Admin-set line; the Delete My Data prompts (chat and Dashboard) mention private notes.
- **An Understanding is per answered message, not per text.** Several texts sent in a row are one message (see the split-out issue below). Replies already go out as several short texts.
- **LangGraph is removed (ADR-0009).** A core `ReplyService` runs the steps in plain Python. The `ConversationEngine` port, the LangGraph adapter and the checkpointer go. First slice, as a pure refactor, so Understanding is built on plain code. Future lookup tools join the reply call's existing tool loop (DeepSeek adapter).
- **Model Call Log, in this PRD (ADR-0010, term in `CONTEXT.md`).** Admin page, one trace per Message or Check-in. Two levels: no content for every User (steps, model, tokens, time, errors, decision shape); full content (instructions, history, tools, tool calls and results, response, reasoning) only for Admins' own chats, Eval runs and local/worktree runs. Removed by Message Retention, Delete My Data and Account Deletion. Not done: full content for everyone (breaks "Admins never see what Users say"); a User's choice to share a Conversation could come later.
- **Knowledge: the Understanding reasons, embeddings find the passage.** Each Knowledge Document gets a "when it helps" description (a field on the document, not file frontmatter: PDFs and text have none, and ADR-0004 keeps it Admin-managed data). The model drafts it when the document is indexed; Admins edit it on the document's page. The Understanding reads the descriptions, decides whether Knowledge fits at all (usually not for Be heard / Just chatting) and which documents, and writes a search phrase. Embeddings then find the best passages only inside those documents, above an Admin-set closeness bar, at most `knowledge_chunks_per_reply`. Frontmatter alone was rejected: one document holds many ideas (Meditations is 42 KB) and listing every document in every call doesn't scale. Later, with a large library: group descriptions by tradition, or show only the closest few by meaning.
- **Users see and delete Threads and the Portrait.** Memories page gains "What I know about you" (the Portrait) and "What's going on in your life" (Threads: story, open or settled, last updated), following `docs/design/zeph-product.html` where it fits. Delete only, no editing (like Memory Items). Deleting must really forget: deleting a Memory Item or Thread rewrites the Portrait without it, in the background right away, and removes the Curiosities it led to. Deleting the Portrait clears it; it is rebuilt at the next Conversation end only if User Memory is on. "Forget that" in chat also works for Threads. Admins see counts only.
- **No backfill.** The platform isn't live; the only User is the owner (an Admin). Existing data can be reset or reseeded.
- **If the Understanding call fails,** the reply still goes: fallback Need, Portrait, newest Summaries, "always include" items and reminded Threads (found without a model call), no Knowledge. The failure shows in the Model Call Log.
- **Split out into their own issues:**
  - Eval dashboard: Admins run Evals on demand from the Dashboard and watch results come in live. Its own PRD (real model cost, long-running background jobs, live progress). Shape so far: test cases become Admin-managed data (editable on the Dashboard, seeded from files); a run can use **draft settings** (a changed prompt, Need or model) to try a change before it goes live, including side-by-side comparisons such as `deepseek-chat` vs `deepseek-reasoner`; a cost estimate before a run; pass/fail, the Judge's reason, tokens and time per case; a failed case opens its full-content trace in the Model Call Log (ADR-0010); Eval code moves into a core service so `make eval` and the Dashboard share it. Grill separately: `.scratch/eval-dashboard/issues/01-run-evals-from-the-dashboard.md`.
- **Understanding Eval, in this PRD.** Run through the real reply path. Cases: Need picked (rant, advice, small talk, Goal slip); a rant gets no fixing; being reminded (sister's wedding finds a 9-month-old open Thread and raises it naturally); leave it alone (same Thread, User struggling with something else); no repeat within a Conversation; brushed off before → not raised too soon; strong mood, unknown cause → gentle probe; Curiosity whose day has come is raised, at most once per Conversation; Knowledge used for a reflective question, not a vent. Also reports Understanding's time and tokens. **Cases are written as data files, not Python**, so they move to the Eval dashboard without a rewrite.
- **Admin controls (per ADR-0004).** Understanding model (starts `deepseek-chat`) and prompt on the Prompts and Models page; Needs get their own admin page like Check-in Kinds; Curiosity limits and the closeness bars (Threads, Summaries, Knowledge) on the Settings page.
  - Wait for the User to finish typing (changes *when* replies happen; same one-process timer problem as `.scratch/scaling/issues/01-run-more-than-one-backend.md`). **Built before Understanding**, so Understandings are made per Message from day one. Term **Message** added to `CONTEXT.md`: everything sent before a pause (texts in a row or an Album), answered with one reply, counts as one toward the Daily Message Limit; the Safeguard still checks each text as it arrives.
  - Keep typing visible on slow replies (small, can ship now).
  - Stronger reply model: no code; `deepseek-reasoner` is already in `available_models`. Compare with the Persona and Knowledge Evals.
